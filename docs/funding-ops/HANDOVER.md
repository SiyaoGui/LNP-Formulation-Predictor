## 4. 方法：研究、核实、复审

### 4.1 一轮研究怎么做

1. 先确认范围和约束，再动手。用户的约束高于一切（第 6 节）。
2. 官方页面一手读取：机构自己的页面、欧盟资助门户、官方指南和规则 PDF。第三方汇总站只用来「找到」，不用来「定」。
3. 日期统一换算成哥本哈根时间：每个截止按机构所在时区的截止时刻折算（布鲁塞尔、美国太平洋时间等），夏令时按机构所在地算。官网只写日期没写钟点的截止按当天 23:59:59；开放日按当天 00:00。我自己假设了钟点的，在胶囊里标「钟点为假设」。
4. 估算日期（按往年节奏或只知道月份）用虚线框，显示「约 N 个月后」；为赶别的项目倒推出的目标日用点线框，不是官方截止。滚动申请、日期未公布、等条件、已排除的条目不倒计时。
5. 每条结论带来源和核实日期。改错时在卡片里写「此前我写……」，让读的人看得到改了什么。
6. 发布前跑自动检查（第 5 节），发布后读回线上版本，和本地文件逐字节比对。
7. 同步更新项目文档里的复审记录。

### 4.2 核实层级（卡片里的用语要统一）

| 用语 | 含义 |
|---|---|
| 自己核对 | 在用户自己的浏览器里打开官方页面读过，页面当时的原文 |
| 助手读取 | 网页读取工具返回的摘要。摘要可能有轻微改写，「页面没写」只代表「摘要里没有」 |
| 未读 / 未核实 | 没打开或没读到。不要补写，不要猜 |

### 4.3 工具与限制

- 浏览器：用户的 Chrome 扩展或应用内置浏览器。读页面优先用文本和结构，不靠截图。
- 不用 curl、wget 或脚本抓网页；读不了就说读不了。不绕过验证码和反爬，不点 cookie 横幅，不提交表单，不注册账号，不输入任何凭据。
- 邮箱连接器：列表预览只显示最早的几封，要读整个线程用 get_thread；不能下载附件（附件要用户自己提供）。过宽的搜索会带出无关的私人邮件，要忽略，不要引用。
- PDF：有的阅读器读不出文字（Innofounder Guidelines 就是这样），这类内容只能标「助手读取」或「未读」。
- 容器里有 Chromium 和 Playwright，可以做页面检查；本窗口的检查脚本没有留下，`tools/check_calendar.py` 是重写的最小版。

### 4.4 复审时发现的错误类型（当检查清单用）

1. 日期张冠李戴：一个页面上有两个项目的日期并排，读错了一栏。
2. 条款已经变了：金额、驻场要求、阶段费用和上一版不同。
3. 我自己写的说法没有出处：「滚动审核」「pro bono」之类，核对后站不住。
4. 此前漏看的限制：表单里的最低金额、会员推荐、是否要先有公司。
5. 用旧版文件的数字：同一份指南的新旧版本给出不同的工时上限。
6. 估算日期被当成官方日期。
7. 官方页面自己前后矛盾：两个页面给出不同的批次日期。要把矛盾写进卡片，不要偷偷选一个。

复审抽样：第一次五轮复审里 190 张卡中 78 张被重新对着官方页面读了一遍，40 张有要更正的地方，38 张核对无误；其余 112 张保留此前的核实结果。

## 5. 日历：结构和更新流程（摘要，细节见 CALENDAR_SPEC.md）

- 形态：一个自包含的 HTML 片段，交给 Artifact 工具发布时由它补上文档外壳，所以文件里没有 doctype、html、head、body 标签，开头是 `<title>` 和 `<style>`。不用外部脚本，只用 Google Fonts；不使用浏览器存储。
- 结构：页头、实时钟（哥本哈根时间，可「改时间」假装现在是别的时刻）、统计格、「接下来几周」行动清单、最近的截止、倒计时说明、统一时间线、四组筛选（状态、区域、资格、时间）、十个分组、页脚的方法说明和版本记录。
- 卡片：`div.fcard`，带 `data-need`、`data-short`、`data-region`；里面有标题行、倒计时胶囊行、字段表、核实备注、官网链接。
- 更新一次的流程：改文件 → `check_calendar.py` 质检 → 浏览器里测 400 px 宽度、键盘 Tab 走一遍、浅色深色两种模式的对比度 → 用 Artifact 工具发布到原来的地址（原窗口用同一个文件路径；新窗口没有原路径，要先 read 读回线上版本，再把原地址作为 `url` 参数传入，不带 `url` 会新建一个、换地址）→ 读回线上版本，逐字节比对 → 更新复审记录 → 版本号加一。

## 6. 一直生效的规则

这些是用户在原窗口里反复确认的，新窗口要照做。

**语言和写法**

- 用中文回复，直接、具体、可执行，不要长篇理论。
- 不用破折号（长的、短的，以及连在一起的两个，都不用）。日期范围写「到」。这条适用于所有回复、邮件草稿和新文件。
- 每个决定写清理由。核实不了的写「未核实」，不要编造。
- 一次最多问用户 3 个问题，其余按合理假设做，并把假设写明。
- 始终保持批判视角，主动找漏洞，不要配合式执行。用户要求做计划时，不要顺手建议新功能、新产品方向或新的转向。

**事实和核实**

- 所有机构名、人名、基金、截止日期、联系方式都要上网核实，查不到标「未核实」。
- 对外材料不能把计划说成已完成。没有独立实验室数据，不写「已验证」。
- 行业访谈的受访者不具名，大药企受访者尤其不要出现在对外材料里。

**操作边界**

- 不替用户发邮件，只起草，发不发由用户定。
- 不绕过验证码、不点 cookie 横幅、不提交表单、不注册账号、不输入任何凭据。
- 不在文件里写用户的个人信息（学籍和学位的具体日期、证件号，以及与个人法律状态有关的措辞，词表在私有层）；不新增第三方邮箱和电话。
- 公开仓库不放：融资材料、申请进展、pitch 策略、评审人姓名、访谈逐条数据、付费意愿金额，也不再往里加硬件技术细节（欧洲专利没有宽限期，公开过的内容不能再当作新颖性基础）。
- GitHub 只推 main：不建分支、不打标签、不强制推送。本地克隆里有一个未跟踪的数据目录（`data/raw/yanes2025_ivr/`），所以只用精确路径的 `git add`，不用 `git add .`。推送由用户在自己电脑上做；不索取、不使用 GitHub 令牌。
- 中东和亚洲的资助轮暂停，等用户明确说「开始」才做。
- 先诊断和排序，用户确认后再做材料；每一步做完停下来等确认。

**邮件草稿的标准**（用户要求的，适用于之后所有邮件）

- 不以「Hello」开头：能查到收件人姓名就直接用姓名，查不到就用「Dear [机构名] Staff」。
- 每封邮件内部写三遍再定稿：初稿，降低 AI 味，再改得更像真人。只交最终版。
- 不用营销腔（例如「would love to connect」），不用破折号和表情。
- 用户发来截图或描述情况时，直接给一封可发的邮件。
