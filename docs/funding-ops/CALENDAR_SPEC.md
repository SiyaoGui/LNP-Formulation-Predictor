# 融资日历说明（对应日历 v32，2026-10-18 发布）

这份说明只讲日历怎么搭、怎么改、怎么测、怎么发布，不含任何卡片内容。卡片内容在私有层。
交接背景见同目录的 `HANDOVER.md`。

---

## 1. 它是什么

一个单文件网页：把丹麦、欧洲、北欧国别、美洲、英国与爱尔兰的基金、资助、创业赛、孵化器、投资人入口和活动，按时间排序，每条标出资格核对结果和核实层级。每个有日期的条目都有实时倒计时。

v32 的规模：210 张卡片，215 个倒计时胶囊（其中 132 个在卡片里，其余在时间线和「最近的截止」里），80 条时间线，约 802 KB。

---

## 2. 文件形态和发布方式

- 文件是一个 HTML 片段，不是完整文档：开头是 `<title>` 和 `<style>`，然后是一个 Google Fonts 的 `<link>`，再是 `<div class="wrap">` 里的全部内容，最后是一个 `<script>`。没有 doctype、html、head、body 标签，因为 Artifact 工具发布时会补上外壳。
- 只允许从 Google Fonts 加载字体（Archivo、IBM Plex Sans、IBM Plex Mono）；脚本全部内联，不加载任何外部脚本；不使用 localStorage、sessionStorage 等浏览器存储。
- 页面标题保持不变（`LipidLens 融资日历`），重新发布时不要改名。
- 两套配色：CSS 变量先在 `:root` 里定义浅色，`@media (prefers-color-scheme: dark)` 里用 `:root:not([data-theme="light"])` 重新定义深色，再有一个 `:root[data-theme="dark"]` 块。所有颜色都走变量。
- 唯一的响应式断点是 `max-width: 480px`；设计目标是 400 px 宽度下没有横向滚动。

## 4. 卡片

骨架（示例内容为虚构）：

```html
<div class="fcard" data-need="S" data-short="示例基金" data-region="dk">
  <div class="fcard-head">
    <div class="fcard-name"><span class="region-tag dk">DK</span>示例基金 <span class="org">· 示例机构</span></div>
    <span class="pill action">截止 12-01 · 单人可投</span>
  </div>
  <div class="cdrow">
    <button type="button" class="cd" data-k="dl" data-t0="..." data-t1="..." data-a="0" data-tg="0" data-h="0"
            data-abs0="12-01 周二 23:59" data-abs1="12-01 周二 23:59" data-det="..." aria-expanded="false">
      <span class="cd-l">申请截止</span><span class="cd-d">12-01 周二 23:59</span><span class="cd-v"></span>
    </button>
    <div class="cd-detail" hidden></div>
  </div>
  <dl class="fcard-grid"><dt>金额</dt><dd class="amt">...</dd><dt>提交</dt><dd>...</dd></dl>
  <div class="fcard-note">核实备注：日期、来源、核实层级、更正……</div>
  <a class="fcard-link" href="https://..." target="_blank" rel="noopener">官网 ↗</a>
</div>
```

- `data-need`：谁能报。S 单人可投，K 需要联合创始人，C 需要 CVR，E 活动，`?` 资格待核实；可以组合（如 `E?`、`EC?`、`S?`）。空字符串表示没有特别条件或不适用。
- `data-short`：筛选和「最近的截止」里用的短名字。
- `data-region`：区域代码，见第 7 节。少数卡（附录里的）没有区域。
- 字段表 `dl.fcard-grid` 的标签不固定，常见的有金额、提交、周期、谁来决定。
- 核实备注是卡片里最重要的部分：写清楚读了哪个页面、哪天读的、是自己核对还是助手读取，以及此前的错误和更正。

## 5. 倒计时胶囊

每个 `button.cd` 是一个日期胶囊，数据全在属性里：

| 属性 | 含义 |
|---|---|
| `data-k` | 种类：`dl` 截止，`ev` 活动日期，`op` 开放日，`rs` 预计出结果，`wn` 窗口（一段时间） |
| `data-t0`、`data-t1` | 开始和结束，Unix 毫秒时间戳；单点日期两者相同 |
| `data-a` | `1` = 估算日期（按往年节奏或只知道月份），显示为虚线框和「约 N 个月后」 |
| `data-tg` | `1` = 为赶别的项目倒推出的目标日，显示为点线框，不是官方截止 |
| `data-h` | `1` = 钟点是我假设的（官网只给了日期），胶囊里标「钟点为假设」 |
| `data-abs0`、`data-abs1` | 印在页面上的日期文字，例如「11-10 周二」「2027-01-10 周日」。跟随机构所在时区，所以可能和哥本哈根时间差一天 |
| `data-det` | 点开后显示的详细说明：日期换算和依据 |

写时间戳时要换算：先确定机构所在时区和钟点，再换成 UTC 毫秒。官网只写日期的截止取当天 23:59:59（机构所在时区），开放日取当天 00:00。

## 6. 倒计时的规则（脚本里的 `describe`、`span`、`approx`、`urg`）

- 时钟用 `Europe/Copenhagen`；钟点换算用两遍偏移修正（`cphToEpoch`），所以跨夏令时的日期不会差一小时。夏令时切换：欧洲 2026-10-25，美国 2026-11-01。
- 精确日期的显示：100 天以上写「N 天」；7 到 99 天写「N 天 H 小时」；1 到 7 天写「N 天 H 小时 M 分」；不到 1 天写 `hh:mm:ss`。
- 估算日期的显示：60 天以上「约 N 个月」；14 到 59 天「约 N 周」；2 到 13 天「约 N 天」；不到 2 天「不到 2 天」。
- 紧急度颜色：不到 1 天 `crit`，不到 7 天 `urgent`，不到 30 天 `soon`，其余 `calm`。
- 滚动申请、日期未公布、等条件、已排除的条目不倒计时，只显示状态。估算日期和目标日不进「最近的截止」。
- 日期全部过去的卡片变灰并标「已过期」。
- 倒计时用用户设备的时钟，设备时间不准，倒计时就不准。关键截止以官网为准。
- 每秒刷新一次；「改时间」只改显示用的 `base` 和 `at`，不碰数据。

## 8. 脚本里的函数

全部在一个立即执行函数里，`'use strict'`。`init` 之后依次接线：

`getNow`（模拟时间）、`partsOf` `cph` `zoneName` `cphOffset` `cphToEpoch`（时区与偏移）、`span` `coarse` `approx` `urg`（显示格式）、`describe`（一个里程碑的状态和文字）、`mkChip` `paintChip` `updateItems` `updateInline` `updateAct` `updatePanel` `updateNext` `updateTimeline`（各区块刷新）、`needHas` `whoOk` `timeOk` `applyFilters` `setActive` `resetFilters`（筛选）、`wire` `jumpTo` `showDetail` `fillSimInput` `applySim` `tick` `loop`（交互和主循环）。

改日期逻辑前先读 `describe`；改筛选前先读 `candidates` 和 `applyFilters`。

## 9. 卡片文字的写法

1. 每条结论后面跟读取日期和来源类型：「（官网 10-18 自己核对）」「（助手读取）」。
2. 估算要说是估算，并写依据：「官网写 11 月中旬，具体日期没写；我取 11-10 到 11-20」。
3. 页面自己前后矛盾时，两个说法都写出来，说明差别，写成「要问机构」，不要悄悄选一个。
4. 更正自己的旧说法时写「此前我写……，现在改为……」，并在页脚的版本记录里留一条。
5. 引号里的原文可能被读取工具改写过，对外引用请以官方页面为准。
6. 不新增第三方邮箱和电话；不写个人身份信息。
7. 不用破折号。时间范围写成「09:00 到 12:00」。

## 10. 发布前的质检

跑 `tools/check_calendar.py`（只读，不联网，不改文件）。依赖：Python 3.9 或更新，`pip install beautifulsoup4`；在 Windows 上还要 `pip install tzdata`（`zoneinfo` 需要它）。`tools/export_cards.py` 同样的依赖。

```
python3 -I tools/check_calendar.py lipidlens-funding-calendar_v32.html --now 2026-11-10T00:00 --upcoming-days 90
python3 -I tools/check_calendar.py <文件> --words <词表文件>     # 另有一个私有词表时
```

它检查：

1. 结构计数：卡片数、各组卡片数、各种胶囊数、区域、行动清单条数、统计格数字。要和统计格、页脚里写的数字一致。
2. 每个胶囊的时间戳换算成机构可能所在的时区后，月、日、星期是否和印出来的日期文字一致（v32：0 个不一致）。
3. 正文里所有「日期 + 星期」的搭配是否在 2026 或 2027 年里对得上（v32：173 处，0 处错）。
4. 正文里的长短破折号（v32：长 0，短 56，全在时间范围里）。
5. 整个文件里的邮箱和电话（v32：55 个邮箱，14 个电话）。
6. 可选的词表计数。
7. 给定天数窗口内的近期日期表。

脚本之外，每次发布前还要手动或用浏览器脚本做这些（原窗口做过，脚本没有留下）：

- 浅色和深色两种模式下所有文字的对比度不低于 4.5（v24 时做过一次，检查了 3,737 处文字，之后新增的内容要再查）。
- 400 px 宽度下没有横向滚动（320 px 下有已知溢出）。
- 所有可点的链接和按钮不小于 24 px；用 Tab 键走一遍，每个控件都有看得见的焦点框。
- 载入时间和节点数：测试环境里约 0.7 秒、约 5,200 个节点，每秒刷新不卡。
- 倒计时跨过夏令时切换日的显示。
- 全页隐私扫描：个人私事、证件日期、第三方姓名邮箱电话。
- 页面顶部统计格的数字和分组标题里的数字一致（v32 发布后发现统计格「活动」写 25、分组写 29，改了重新发布）。

## 11. 发布和回读比对

1. 用 Artifact 工具发布到原来的地址，保持原链接：在原窗口用同一个文件路径；在新窗口没有原路径，先 read 读回线上版本，再把原地址作为 `url` 参数传入（不带 `url` 会新建一个、换地址，旧链接作废）。第一次发布才需要图标和标题，重新发布不要再传图标。
2. 发布后用 Artifact 工具的 read 读回线上版本，和本地文件逐字节比对（长度和 SHA-256）。不一致就找出原因，不要接受。
3. 更新项目文档里的复审记录：版本号、卡片数、胶囊数、改了什么、还有什么没核实。
4. 对用户只写一句话说明发布了什么；不要在对话里贴 artifact 地址（界面会显示卡片）。

## 13. 已知限制

- 数据截止 2026-10-18，行动清单大部分已过期。
- 日历不是逐条核实过的清单，核实层级写在每张卡的备注里。
- 有 55 个第三方邮箱、14 个电话号码、56 处时间范围的短破折号、若干处个人信息类措辞，是早期各轮留下的，待用户决定后处理（任务 T13、T14）。
- 320 px 宽度下有 5 个长标签溢出。
- 倒计时依赖设备时钟。
- 外壳由发布工具补上，所以本地直接双击打开这个文件时，浏览器会按怪异模式渲染，也没有字符集声明，中文可能乱码，样式也可能与线上不同；本地预览要自己补一个最小外壳（doctype、charset、viewport）。
- 页头的三个小标签含个人信息，发布 v33 时要重写，不要原样保留（具体内容见私有层的补充文档）。
