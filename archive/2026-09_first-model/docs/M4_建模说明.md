# M4 · 定 target → split → 训模型 → 报一个可引用的指标

## 一、产出

- `train_m4.py`：训练脚本，从 M3 的 `feature_matrix.parquet` 单一输入即可完整重跑
- `m4_model.joblib` / `m4_feature_columns.joblib`：最终模型（用全部筛选后数据训练）+ 对应的特征列名顺序
- `m4_cv_predictions.csv`：5折交叉验证的逐行预测值 vs 真实值，可以自己核对
- `m4_per_source_metrics.csv`：按来源拆分的指标

## 二、模型选择：临时换成了 HistGradientBoostingRegressor，不是 XGBoost

原计划用 XGBoost，但这次环境的网络代理不稳定，xgboost 的 wheel 包（不同版本 130～300MB 不等）反复下载到一半就断线，试了 3 个版本、十几次重试都没能完整装上。改用 **sklearn 自带的 HistGradientBoostingRegressor**——同属梯度提升树家族，效果不会有本质差异，而且原生支持缺失值（不需要额外插补），零额外安装成本。如果之后网络环境稳定了，`train_m4.py` 换成 `XGBRegressor` 是几行代码的事，其余部分（target定义、过滤逻辑、特征选择）都不用动。

## 三、target 怎么定的

选了 `particle_size_nm`（粒径）——三个数据源里覆盖率最高（1736/1934，89.8%），也是跨全身给药/局部给药场景都通用的一个物理指标，比包封率（29%覆盖）、表面电位（22%覆盖）这些更有统计基础。

**关键处理：过滤掉了长尾极端值**。原始粒径分布从17nm一路拖到113万nm（1.13毫米！），中位数只有111nm，均值却被拉到3538nm——查了一下这些超大值，几乎全部来自两种情况：Luciani里 `formation_ok=0` 的失败配方（脂质没形成正常颗粒、结成了团块）、以及 PMC_IVR 里少数刻意做成微米级的多层囊泡（process_notes 的 structure_type 字段写着 MLV/LMVV，这是另一类真实但物理机制完全不同的颗粒体系）。这两种情况都不该和纳米级颗粒放在同一个回归任务里，所以统一按纳米药物递送领域的标准定义过滤到 **≤1000nm**，同时单独确认了 Luciani 里没有"粒径不大但依然是失败配方"的漏网之鱼一并排除。过滤后剩 1564 行（950 LNP_Atlas + 427 Luciani + 187 PMC_IVR），分布变得正常（17-982nm，中位数102nm）。

target 本身做了 **log10 变换**（粒径右偏分布的标准处理），报告的 RMSE/MAE 已经换算回原始 nm 尺度方便直接读。

## 四、特征怎么选的

排除了标识列（source_dataset等）、其它target列（不能拿pdi/zeta去预测particle_size，那是泄漏）、文本列（process_notes）、以及 M2 阶段的审计标记列（`ratio_order_was_ambiguous` 等——这些是数据质控过程的元信息，不是真实化学信号，混进特征会让模型学到一些没有物理意义的捷径）。

指纹部分：M3 产出的是每个角色512位，这次为了在算力预算内跑完，先降到每个角色64位——测过对比，64位和512位的结果几乎一样（R²=0.432 vs 0.425，descriptor-only版本），说明对这个target来说，分子量/LogP/TPSA这类基础描述符已经抓住了大部分信号，指纹分辨率暂时不是瓶颈。全量512位版本留作后续有更长算力预算时的加强项。

缺失值**没有做零向量填充**（这是对之前讨论方案的一个修正）：树模型原生支持NaN、会学习"缺失时往哪边走"，比人为填0更合理——填0会把"没数据"和"真实值恰好是0"混为一谈（比如 NumHDonors=0 是很多分子的合法真实值）。

## 五、结果：整体过得去，但分来源拆开看问题很明显

**5折交叉验证：R²=0.432（log空间），RMSE=99.4nm，MAE=41.5nm**——作为"默认参数、不调参"的第一版baseline，这个数字本身是可以用的。

**但分来源拆开看，差异很大，这是这次建模最重要的发现：**

| 来源 | n | R² | RMSE | MAE |
|---|---|---|---|---|
| LNP_Atlas | 950 | **0.635** | 41.6nm | 23.8nm |
| Luciani | 427 | 0.398 | 154.8nm | 80.1nm |
| PMC_IVR | 187 | **-0.324** | 138.4nm | 43.0nm |

LNP_Atlas 单独看表现不错（R²=0.635），Luciani 中等，**PMC_IVR 是负的**——负R²意味着模型预测得比"直接猜训练集均值"还差。这不是bug，是三个来源池化训练暴露出的真实问题：LNP_Atlas样本量最大（950/1564，61%），模型学到的很可能主要是LNP/LNP样式配方的规律，这套规律套到PMC_IVR（经典脂质体+具体小分子药物，化学体系不同、样本量也最小）上是失效的。这和之前讨论过的"三个数据源领域不完全一致、池化训练要小心"是同一个问题在建模阶段的具体体现——如果只报整体R²=0.432，会掩盖PMC_IVR这块完全没学到东西的事实，所以按来源拆开报是必须的，不是可选项。

## 六、这个数字能不能直接拿去用在申请材料里

**能引用，但要带着分来源的拆解一起说，不能只说R²=0.432这一个数字。** 一个合理的表述方式是："在过滤掉失败配方和非常规颗粒体系后的1564条配方上，粒径预测baseline整体R²=0.43；其中数据量最大、最主流的LNP体系（950条）单独达到R²=0.64，说明方法论在数据量充分时是有效的；同时也如实发现了跨异构数据源池化训练的局限（小样本源迁移效果差），这是下一步数据/建模需要针对性解决的方向"——这种说法比藏起弱点更有说服力，也符合之前商量好的"主动暴露问题，别等被问"的原则。

## 七、已知局限 / 下一步

1. 完全没调参（按计划就该这样），如果要往上冲分数，`HistGradientBoostingRegressor` 的 `max_leaf_nodes`/`learning_rate`/`max_iter` 都还没动过默认值。
2. 512位全量指纹版本因为算力预算限制没跑完整的5折CV，64位版本的结果显示指纹分辨率暂时不是瓶颈，但这个结论只在当前样本量/target下成立，不代表以后也一定如此。
3. PMC_IVR的负R²有两个可能原因没有分开验证：(a) 样本量太小（187条）导致CV本身噪声大，(b) 真实的跨体系迁移失败。如果之后要认真解决这个问题，值得单独给PMC_IVR切一个source-aware的模型或者加source_dataset本身作为强特征做对比实验。
4. 目前预测的是"能不能形成一个正常尺寸的颗粒"，跟之前讨论过的Track A/Track B领域错配是同一件事——这套模型服务于全身给药场景的配方可行性预测，不直接预测透皮/毛囊渗透相关的指标。

## 八、2026-07-31 更新：修复跨论文泄漏后重新评估（重大发现，改写了之前的结论）

**背景**：之前的5折CV是行级随机split——同一篇论文/同一批实验的行可能同时出现在train和test里。检查发现这个风险是真实存在且很严重的：`paper_doi`分组后，**Luciani全部427行来自同一篇论文（唯一一个DOI），LNP_Atlas横跨60个分组（55个真实DOI+5行无DOI各自单独成组），PMC_IVR横跨30个DOI**。行级随机split下，每一折的训练集里都混有来自"测试集同一篇论文"的其它行，模型很可能在做类似"记住这篇论文的配方长什么样"这种插值，而不是真的学会组成→粒径的普适规律。

**修复方法**：把CV换成`GroupKFold`，按`paper_doi`分组（缺失的5行各自独立成组，不与任何行共享），保证同一篇论文的行只会出现在train或test其中一边。`train_m4.py`已更新为同时跑新旧两种方法并列对比，`m4_per_source_metrics.csv`现在有`cv_method`列区分。

**结果——整体R²从0.432掉到-0.044**：

| | 旧（行级随机，有泄漏） | 新（按论文分组，无泄漏） |
|---|---|---|
| 整体 | R²=0.432 | **R²=-0.044** |
| LNP_Atlas (n=950) | R²=0.635 | **R²=-0.104** |
| Luciani (n=427) | R²=0.398 | **R²=0.003** |
| PMC_IVR (n=187) | R²=-0.324 | R²=-0.201（唯一变好的） |

**这不是bug，是真实结果**——已核对分组逻辑（LNP_Atlas分组数60=55真实DOI+5独立占位符，与源数据独立核实的唯一DOI数吻合）、核对了每折样本量总和对得上（1564行）。之前"整体R²=0.432、LNP_Atlas单独R²=0.635表现不错"这个结论，相当一部分是同一篇论文的行同时出现在train/test造成的插值假象，而不是模型真的学会了跨论文/跨配方体系的普适规律。**之前M4文档里"LNP_Atlas样本量最大、模型学到的规律是有效的"这个说法，现在看是站不住的，应该撤回。**

**一个重要的统计学附加说明（Luciani那一行的数字比其它两行更不可靠）**：因为Luciani是单一分组，GroupKFold的5折里只有1折的test集包含Luciani（这一折train集里Luciani是0行——完全没见过就要预测），另外4折的test集里Luciani是0行。也就是说Luciani的R²=0.003不是5折平均出来的，是**单次train/test划分**的结果，比LNP_Atlas、PMC_IVR（分组数多、能在5折间相对均匀打散）的数字方差更大、更不能代表稳定的泛化能力估计。

**对九月申请的影响，需要你决定怎么走，我没有替你做这个决定**：这个结果好坏参半——往好里说，这是方法论严谨性的证据（自己发现问题、自己修复、诚实报告，这正是之前反复讨论的"主动暴露问题"原则的体现）；往坏里说，一个≈0甚至为负的R²本身很难成为申请材料里"我们的技术有效"的证据，不管框架写得多诚实，评审看到这个数字第一反应大概率是"这个模型现在不work"。这已经不是"要不要报一个更低的数字"这么简单，而是"现在这个数字要不要/怎么出现在申请材料里"的策略问题。

## 九、2026-07-31 同日更新：补齐工艺特征后的结果（部分改善，未完全解决）

**诊断**：把分组CV拆到"组内标准差27.2nm vs 组间标准差37.0nm"这一步之后发现，不同论文之间的粒径系统性差异比同一论文内部的差异还大，但当时的特征矩阵里没有任何工艺信息——顺着这个线索回查三个原始数据源，发现工艺参数其实都在，只是被当成大段文本塞进了`process_notes`（从未拆解、且`process_notes`本身在M4里是被排除的文本列）：

- LNP_Atlas 的 `synthesis_info` 是`key: value`结构化文本，`synthesis_method`覆盖率100%
- PMC_IVR 原始数据库里有独立的 `formulation_CPPs_CQAs` 表（`preparation_method`/`encapsulation_method`/孵育温度时间/测量仪器型号`PS_instrument`），之前只用了其中的`structure_type`做异常值过滤
- Luciani 的 `CHIP`/`FRR`/`TFR` 也是同样被拼进了文本

新增6个结构化工艺列（`prep_method_std`/`device_or_chip_std`/`measurement_instrument_std`/`flow_ratio_imbalance`/`total_flow_rate_ml_min_std`/`process_temp_c_std`），并入`merge_schema.py`→`featurize_m3.py`→`train_m4.py`，重新做分组CV：

| | 补工艺特征前 | 补工艺特征后 |
|---|---|---|
| 整体 | R²=-0.044 | **R²=-0.000** |
| LNP_Atlas | R²=-0.104 | **R²=0.048**（由负转正）|
| Luciani | R²=0.003 | R²=-0.028（单折结果，本身方差就大，这个方向的波动不能过度解读）|
| PMC_IVR | R²=-0.201 | R²=-0.160 |

同时也试了：LNP_Atlas单独建模+工艺特征（不池化其它两源）——结果反而更差（R²=-0.16~-0.21），说明池化其它来源提供的样本量/多样性帮助比"域外数据带来的噪声"更大，不是"数据源越纯越好"这么简单；以及正则化超参数（帮助很小，不是瓶颈所在）。

**如实评估**：工艺特征这条线确实是有效信号（不是瞎猜）——旧口径(行级随机split)下R²从0.432跳到0.661，证明这些特征让模型看到了真实存在的规律；但严格的按论文分组评估下，提升有限——整体仍在0附近，只有LNP_Atlas由负转正、且数值很小(0.048)。**这还不是一个能在申请材料里站得住的"预测有效"的数字**，是一个"方向对了、但没做完"的中间状态。剩下能想到的路径（更细的工艺特征、更换建模方式、限定到更窄的可比子集）预期收益和需要投入的时间都不确定，是否继续投入需要权衡剩余天数。
